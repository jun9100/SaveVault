# SaveVault 云端（game-save）优化计划

2026-11-03。本计划接在 [`INTEGRATION_ROADMAP.md`](INTEGRATION_ROADMAP.md) 的 P0–P5 之后。
那里的安全规则全部沿用，任何一条都不放松：
- 内容血统决定能否前进；
- 按 CAS 写入；
- 冲突副本不可删；
- 恢复前留安全副本；
- 按类型隔离命名空间；
- 首次验证不用唯一存档。

## 现状

已经有的：
- 不可变归档、按范围的 CAS 头、冲突副本保留；
- Eden v2 协议、SaveVault 原生类型范围（`pc`、`switch`、`emulator-*`）、只读状态接口；
- 管理网页、Bark 通知、保留策略、完整性校验和 Prometheus 指标。

缺口（按对使用的影响排序）：

1. **云端没有“同一个游戏”。** Android 按“来源 × 游戏”各存一个范围（`android-<类型>-<哈希>`），
   PC 用自己的命名。只有 Root 读到的单一位置 Switch 存档，才用 `switch-<TitleID>` 跨设备。
   所以手机和 PC 玩同一款游戏不能接力，网页上同一款游戏也会分散成好几行。
2. **Switch 存档可能有两个写入方。** Eden 自己的同步（Eden 协议）和 SaveVault（原生范围）
   都会备份同一份 Switch 存档，两边各自前进、互不知道。
3. **已有功能还没在实机上验证。** P5 隔离回归此前一行都没跑。GitHub 上 game-save 最新的
   Release 仍是 `v1.0.0`，和路线图里的 `v1.4.1` 对不上。按发布规则第 2 条，Android 的 P5 行
   通过前不发布 APK。
4. **所有设备共用一个同步密钥。** 丢一台设备，只能给所有设备换密钥。
5. **网页只能看。** 不能下载某个版本、不能在冲突之间选择，也不能按游戏清理。
6. **名称和封面由各端各自抓取。** 国内网络下不稳，自定义封面也不能同步。

## 阶段

### C0 先把已有的跑稳（进行中）

- 用本机临时服务、无 Root 的 Android 手机和 Windows 虚拟机执行 P5，只用回归夹具。
  - 服务端行用 `scripts/p5_service_rows.py`，结果记在 [`P5_RESULTS.md`](P5_RESULTS.md)。
- 核对并发布 game-save 新版本，附版本号、镜像标签、发布说明，以及数据目录的备份与回滚清单。
- 演练“数据目录备份 → 新容器恢复”（GS-05）。

### C1 跨设备的“同一个游戏”

- **服务端**：在现有范围之上加一层“游戏”。逻辑游戏 = 类型 + 规范 ID，下面挂多个范围。
  归档、CAS 和冲突规则都不变。
- **规范 ID**：按 Switch TitleID、Steam AppID、PSP 游戏编号、安卓包名自动识别；
  识别不了的，由用户手动关联。
- **客户端**：能看到其他设备的存档，并显式恢复到本机位置（先留安全副本）。
  只有父链能证明连续时，才自动接力。
- **网页**：按游戏展示。

### C2 Switch 双写入方

同一 TitleID 同时有 Eden 头和 SaveVault 范围时，以 Eden 为准。
SaveVault 只做本地快照，并只读展示 Eden 的云端状态。

### C3 设备与权限

- 每台设备一个独立令牌，通过配对码或二维码导入。
- 网页上可以改名、吊销令牌。
- 原来的共享密钥保留一段兼容期。

### C4 网页管理增强

- 下载任意版本。
- 冲突对比，选定其中一个作为新头（走 CAS）。
- 按游戏看占用并手动清理；冲突副本仍不可删。

### C5 元数据与封面服务

- 服务端缓存封面。
- 统一名称表。
- 自定义封面跨设备同步。

### 以后再说

- 客户端加密：SaveVault 的归档在 NAS 上是明文 ZIP。
- 多用户。

## 顺序

C0 → C1 → C2 → C3/C4/C5。每个阶段单独开 PR。服务端与客户端的改动分开提交；
协议变化要等依赖它的客户端发版后，才算交付。
